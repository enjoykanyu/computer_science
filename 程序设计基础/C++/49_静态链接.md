其他语言 vs C++：在 Java（Maven/Gradle）、C#（NuGet）、Python（pip）、JavaScript（npm）中，引入第三方依赖只需一行命令或几行 XML。但在 C++ 中，由于历史原因与平台原生性，库管理往往是新手的“劝退噩梦”

二进制文件 vs 源码构建：该怎么选？
- 严谨正式项目：强烈推荐直接拉取第三方库的源代码，作为子项目（Subproject）放进 Solution 里一起编译。优势：便于断点单步调试库内部代码、方便定制修改源码、且完全杜绝编译器 ABI 不兼容问题。
- 快速原型/小型项目：直接下载并链接官方提供的预编译二进制文件（Precompiled Binaries），速度最快、配置最省事。本讲聚焦于二进制静态链接

### 头文件（include）与二进制库（lib）
将一个C++库文件解压
解压后的目录解剖
解压后会发现一个标准的 C++ 库必定由两大部分组成：
1. include/ 目录：存放头文件（.h）。提供符号声明（Declarations），告诉编译器有哪些函数、类、结构体可以用。
2. lib/ 目录：存放预编译好的二进制文件。在 Windows 下通常分为：
    - glfw3.lib：真正的静态库（Static Library）。体积较大（数百 KB），包含库的完整二进制实现机器码。
    - glfw3dll.lib：导入库（Import Library）。体积很小，仅包含指向 DLL 的符号地址导出表。
    - glfw3.dll：动态链接库（Dynamic Link Library）。运行时才加载的共享二进制

静态链接（Static Linking）的官方底层定义（cppreference / OS Loaders）：
- 静态链接发生在链接阶段（Link Time）。链接器（Linker）会将 glfw3.lib 中被你的代码实际调用到的那些编译好的机器指令字节，直接原地复制、打包并缝合进你最终生成的 HelloWorld.exe 二进制文件内部。
- 静态链接的压倒性优势：
    - 1. 零外部 DLL 依赖：运行时不需要在同一目录下附带 .dll，单文件即可运行；
    - 2. 支持全程序链接时优化（LTO / LTCG）：链接器能在跨模块视角下直接把库函数进行内联展开（Inlining），消除函数调用开销，执行速度往往优于动态链接

痛点：绝对路径 vs 相对路径
- 如果在 VS 属性里直接写 C:\Users\Yan\Documents\...，别人克隆代码后必然因找不到路径而编译失败。
- 正确姿势：使用 Visual Studio 的内部构建宏 $(SolutionDir)。
    - $(SolutionDir)：代表 .sln 文件所在的绝对路径（末尾自带有反斜杠 \）
    
### #include <...> vs #include "..." 的本质差异
尖括号 <>：指示预处理器优先在编译器的系统包含目录以及通过 -I / 附加包含目录指定的目录中搜索。
双引号 ""：指示预处理器先在当前源文件（main.cpp）所在的同级目录搜索，如果找不到，再退化去搜索附加包含目录
建议：工程内自己写的头文件用 ""，外部第三方依赖库统统用 <>，语义一目了然

### 无法解析的外部符号
```cpp
#include <iostream>
#include <GLFW/glfw3.h>

int main() {
    int a = glfwInit(); // 调用库函数
    std::cout << a << std::endl;
}
```
编译成功但运行报错：error LNK2019: 无法解析的外部符号 _glfwInit，该符号在函数 _main 中被引用
fatal error LNK1120: 1 个无法解析的外部命令

为什么编译不报错，而链接报错？
因为 #include <GLFW/glfw3.h> 内部仅仅写着一行：
```cpp
GLFWAPI int glfwInit(void); // 这里末尾是一个分号！只有声明，没有函数体！
```
编译阶段只看声明，编译器看到有这个函数原型，就放心通过了；但在链接阶段，链接器必须把机器码中的这行调用跳转（call 指令）绑定到一个真实的内存机器码地址上。此时由于我们还没告诉链接器去哪里找这行代码，链接器就陷入了“找不到符号定义”
在 main.cpp 里面亲手写一个假定义：
```cpp
int glfwInit() { return 0; }
```
再去生成，LNK2019 错误立刻消失！这完美证明了：头文件只管“有这个东西”，库文件（lib）才管“真正干活的机器码”

### 链接静态库 glfw3.lib
1,把真正的库二进制文件喂给链接器
告诉链接器去哪个目录找 lib 文件（附加库目录）
- 项目属性 $\to$ 链接器（Linker） $\to$ 常规（General） $\to$ 附加库目录（Additional Library Directories）。
- 填入相对路径：
```cpp
$(SolutionDir)Dependencies\GLFW\lib-vc2015
```
2,明确告诉链接器要链接的具体文件名称（附加依赖项）
- 项目属性 $\to$ 链接器（Linker） $\to$ 输入（Input） $\to$ 附加依赖项（Additional Dependencies）。
- 直接填入文件名：glfw3.lib 
调试若返回值 1 代表 GLFW 成功初始化
  
### 抛弃头文件，为什么必须加 extern "C"
如果我们完全不写 #include <GLFW/glfw3.h> 呢？
做了一个实验：把 #include 彻底删掉！
如果直接在代码顶部手动写声明：
```cpp
int glfwInit(); // 手动声明函数存在

int main() {
    int a = glfwInit();
    std::cout << a << std::endl;
}
```
居然再次报出 LNK2019: 无法解析的外部符号！
明明库已经配好了，为什么自己声明就链接不上？

### 根源剖析：C++ 名字修饰
C++ 拥有函数重载（Overloading）特性：
编译器为了区分同名但不同参数的函数，会在编译时给函数名“偷偷改名”。例如 C++ 编译器会把 int glfwInit() 编译成类似 ?glfwInit@@YAHXZ 这样一段带有类型签名编码的怪异符号。
但是，GLFW 是纯 C 语言编写的库！
C 语言没有函数重载，在用 C 编译器生成 glfw3.lib 时，符号表里导出的名字就是赤裸裸的 _glfwInit。
链接器的困境：
C++ 编译器拿着经过名字修饰的 ?glfwInit@@YAHXZ 去 glfw3.lib 里面搜索，而库里面只有 _glfwInit，两者名字对不上，因此链接器报“找不到符号”
### extern "C"
告诉C++编译器：请按C语言的方式来对待这个符号，不要对其进行任何名字修饰：

```cpp
extern "C" int glfwInit(); // 强制使用 C 语言链接规范！

int main() {
    int a = glfwInit(); // 完美链接成功！控制台输出 1
}
```
头文件里面其实早已帮我们包好了这一层宏保护（#ifdef __cplusplus extern "C" { ... }）。头文件不是魔法，它本质上就是帮剔除了人肉手写这一大堆带extern "C"的函数声明
